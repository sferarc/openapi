# Generator pipeline

## Steps

1. `pnpm generate --filter=<package>` runs the package's `generate` script through Turborepo (`package.json`, `turbo.json`). Turborepo builds `@sferadev/openapi-utils` first (`"dependsOn": ["^build"]`). The task is uncached (`"cache": false`) because it reads a remote spec, so every run fetches the live spec.
2. The script deletes `src/generated/` and runs `kubb generate` (for example `packages/vercel-api-js/package.json`).
3. The package's `kubb.config.ts` fetches the live spec with `fetchSpec` (a URL, with a timeout; `packages/openapi-utils/src/kubb/spec-transforms.ts`), applies whichever transforms that spec needs, and spreads `baseConfig` from [[shared-utils]].
4. kubb writes three files into `src/generated/` (`packages/openapi-utils/src/kubb/index.ts`):
   - `types.ts` from `@kubb/plugin-ts`, enums as `as const` objects.
   - `components.ts` from the repository's own client plugin (`packages/openapi-utils/src/kubb/plugin.ts`), which emits one function per operation plus `operationsByTag`, `operationsByPath` and `tagDictionary`.
   - `schemas.ts` from `@kubb/plugin-zod`, with a `// @ts-nocheck` banner, unless the config passes `skipZod`.
5. kubb's `postGenerate` runs `biome check --write` on the output, because CI gates on `biome check` and kubb's own formatting leaves import order unsorted (comment in `packages/openapi-utils/src/kubb/index.ts`).

## Per-spec fixups

Each `kubb.config.ts` carries the transforms its spec needs, so the fixups differ per package:

- `packages/vercel-api-js/kubb.config.ts` uses most of the shared transforms, renames a few operation IDs and repairs a malformed `groupIds` schema. It also gives `writeSessionFiles` (`POST /v2/sandboxes/sessions/{sessionId}/fs/write`) a required `application/gzip` binary request body, unless the spec declares one: the live spec describes the tarball upload only in the description and has no `requestBody` (checked 2026-10-29), so the generated operation had no `body` and sent the request without one (`.changeset/vercel-sandbox-write-files-body.md`). The container registry blob and manifest uploads under `/v2/{teamSlug}/{projectSlug}/{repositoryName}/` also lack a `requestBody`; they are left alone, as the upload UUID and the manifest digest come back in the `Location` and `Docker-Content-Digest` response headers (operation descriptions), which the fetcher does not return.
- `packages/vercel-api-js/kubb.config.ts` and `packages/v0-api/kubb.config.ts` keep the spec's keys as they are. Both used to end with `camelCaseProperties`, which renamed every key, so `application/json` became `applicationJson` and `$ref` became `ref`; see [[decisions/2026-10-27-keep-spec-keys]].
- `packages/keycloak-api/kubb.config.ts` generates twice: the admin API from Keycloak's published spec and the account API from the checked-in `specs/account.yaml`, selected by `KUBB_TARGET` (`packages/keycloak-api/package.json`). Before the shared transforms it rewrites three admin request bodies that Keycloak reads as a raw `String` but the spec types as a JSON string, which the fetcher JSON-encodes into a quoted string (`fixStringBodies`, `.changeset/keycloak-raw-string-bodies.md`): the authz `policy` and `permission` creates under `/admin/realms/{realm}/clients/{client-uuid}/authz/resource-server/` take a `PolicyRepresentation`, as `PolicyService.create` parses the payload with `JsonSerialization.readValue` into one, and `client-description-converter` keeps only its `text/plain` content, since each converter's `isSupported` wants the text to start with `{` (OIDC, with `redirect_uris`) or `<` (SAML `EntityDescriptor`), so a quoted string got `Unsupported format` (`OIDCClientDescriptionConverterFactory.java`, `EntityDescriptorDescriptionConverter.java` and `PolicyService.java` in keycloak/keycloak `main`, checked 2026-10-30). No request was sent to a Keycloak server. Five other admin bodies are also typed `string`: the realm import and `partialImport` read an `InputStream` and are generated as `unknown`, the organization `members` and `identity-providers` adds strip surrounding quotes from the id (keycloak/keycloak#34401), and the `membership-type` update binds a `MembershipType` enum with Jackson, which needs the quotes. It also types the `type` path parameter of the workflow `activate` and `deactivate` operations (`POST /admin/realms/{realm}/workflows/{id}/activate/{type}/{resourceId}` and `.../deactivate/...`) as the string enum `USERS`, `CLIENTS` (`fixWorkflowResourceType`, `.changeset/keycloak-workflow-resource-type.md`): the spec declares it `type: object`, so the generated path type was `object` and a name such as `"USERS"` failed to compile, while JAX-RS binds the segment to the `org.keycloak.models.workflow.ResourceType` enum by name, whose only constants are `USERS` and `CLIENTS` (`ResourceType.java` and `WorkflowResource.java` in keycloak/keycloak `main`, checked 2026-10-30). No request was sent to a Keycloak server.
- `packages/netlify-api/kubb.config.ts` drops the `/api/v1` prefix from spec paths that repeat it (`stripBasePathPrefix`, `.changeset/netlify-site-env-path.md`). The Swagger 2 spec declares `basePath: /api/v1` and lists `getSiteEnvVars` as `/api/v1/sites/{site_id}/env`, and the fetcher prepends the base path, so the client requested `/api/v1/api/v1/sites/{site_id}/env`; unauthenticated, that URL answers 404 and `/api/v1/sites/{site_id}/env` answers 401 (checked 2026-10-30). It was the only such path in the spec.
- `packages/zoom-api-js/kubb.config.ts` fetches the Meetings spec from `https://developers.zoom.us/api/zoap/meetings/methods/`. Zoom's redesigned developer site dropped the old `/api-hub/meetings/methods/endpoints.json` path, which now returns 404 (checked 2026-10-20).
- `packages/litellm-api/kubb.config.ts` fetches the full LiteLLM proxy spec from `https://docs.litellm.ai/openapi.json` (OpenAPI 3.1.0, 737 paths, checked 2026-10-20). The earlier hosts `www.demo.litellm.ai` and `api.litellm.ai` stopped serving it or only exposed a few billing and model catalog operations (f15416b, from the earlier monorepo). The switch removed those four operations from the client, recorded as a major in `.changeset/litellm-spec-source.md`.
- `packages/cloudflare-api-js/kubb.config.ts` drops the `application/javascript` and `text/javascript` entries from the `workers_script_upload` and `workers_namespace_upload` request bodies, which the spec describes as raw script in service-worker syntax only (checked 2026-10-30). With them listed first, the request body fallback in `packages/openapi-utils/src/kubb/adapter.ts` picked raw JavaScript, so `workerScriptUploadWorkerModule` and `namespaceWorkerScriptUploadWorkerModule` could not upload an ES module Worker with its `metadata`; both now send the `multipart/form-data` body (`.changeset/cloudflare-worker-multipart-upload.md`).
- `packages/cloudflare-api-js/kubb.config.ts` runs `optionalReadOnlyInRequestBodies` after deduplicating components. The spec marks server-set fields such as a ruleset's and a rule's `id`, `version` and `last_updated`, an email security allow policy's `id`, `created_at` and `last_modified`, or a Worker's `id`, `created_on`, `updated_on` and `references`, both `readOnly` and required, so creating a ruleset, a ruleset rule, an allow policy or a Worker failed to type-check without them. It adds 43 `Writable` request types, plus 12 copies of the enums inside them, and changes only request body types (local regeneration on 2026-10-30, live spec otherwise unchanged; `.changeset/cloudflare-read-only-request-fields.md`, `src/client.test.ts`). The other seven specs have no required `readOnly` property a request body reaches beyond what kubb already omits (checked 2026-10-30), so they do not run it.
- `packages/cloudflare-api-js/kubb.config.ts` runs `inlinePathServers` before `camelCasePathParams`. The K2 stream data endpoints (`/produce` and the `/subscriptions` paths, nine operations such as `postK2Produce` and `postK2SubscriptionsBySubscriptionIdConsume`) declare the path-level server `https://{stream_id}.k2.cloudflarestorage.com`, so they used to call `https://api.cloudflare.com/client/v4/produce`; they now take a required `streamId` path parameter and call the stream's host (live spec checked 2026-11-01; `src/client.test.ts`, `.changeset/cloudflare-k2-stream-host.md`). A local regeneration on 2026-11-01 changed only those operations and their `Path` types.

## Scheduled regeneration

`.github/workflows/update-openapi.yml` regenerates every client in a matrix, formats with `pnpm check:fix`, and runs `.github/workflows/scripts/changes.ts`, which writes at least one changeset whenever the package has changes. It streams `git diff`, reduces it to the added and removed exported declarations of `src/generated/{types,components}.ts` and the lines changed inside an export both sides keep, under a `~export ...` line naming it, capped at 60,000 characters (`summarizeDiff` in `scripts/changeset.ts`). Hunk headers are dropped, because git names the enclosing export in them and the model read that as a removal (#195), and asks an OpenAI model for `patch` or `minor` entries (`generateText` with `Output.object`). The root `pnpm tsc` typechecks the script through `.github/workflows/scripts/tsconfig.json`, so a breaking `ai` or `@ai-sdk/openai` bump fails CI instead of the next spec run. Without `OPENAI_API_KEY`, or when the call fails or returns nothing, it writes `"<package>": patch` "Regenerate from the latest <package> OpenAPI spec." A removed `export async function` always adds a `[BREAKING]` minor entry, whatever the model says. Only a failure to read git state exits non-zero, which stops the job before the PR is opened. The workflow then opens or updates one PR per package on the branch `openapi/<package>` and enables auto-merge on it. The commit is authored and committed as `sferarc-hq[bot] <335065863+sferarc-hq[bot]@users.noreply.github.com>`, the App whose token pushes it; before 2026-10-31 the committer was the owner and the author defaulted to the actor that triggered the run (the owner on a manual dispatch). The hourly schedule only runs when the repository variable `SPEC_UPDATES_ENABLED` is `true`; a manual dispatch always runs (comment in the workflow). Each matrix job has `timeout-minutes: 45`, so a stuck generate fails that package instead of a manual run going on for the 6 hour default; the hourly cron already cancels the previous run through `cancel-in-progress`. See [[development/release]] for what a merged changeset does.

`SPEC_UPDATES_ENABLED` was unset until the owner set it to `true` on 2026-10-26 at 10:23 UTC (`gh variable list`); the hourly runs before that report `skipped`, and the `if:` itself is correct. `OPENAI_API_KEY` is a repository secret.

The first scheduled runs (for example run 40427642054, 2026-10-27) generated every client but failed in `Create Pull Request` for the five packages with changes: `git push` ended in `fatal: could not read Username for 'https://github.com'`, because the org PAT `GIT_TOKEN` the workflow used is rejected by GitHub since about 2026-10-23 (sferarc/hq `kb/company/infrastructure.md`). The workflow now mints a `sferarc-hq` App installation token right before `Create Pull Request`, scoped to this repository with `contents` and `pull-requests` write, and uses it for the PR and for `gh pr merge --auto`; the App is installed here (it opened #73). `HQ_APP_ID` and `HQ_APP_PRIVATE_KEY` are organization secrets with selected repositories, and on 2026-10-27 that list was `hq`, `infra`, `nuclom`, `pgbeam` and `platform` (`gh api orgs/sferarc/actions/secrets/HQ_APP_ID/repositories`), declared in sferarc/infra `github/adopted.ts`. The mint works here since 2026-10-28: scheduled run 40695148262 opened #101 as `app/sferarc-hq` from `openapi/keycloak-api`, and every scheduled run since has succeeded and opened its spec PRs as the App, up to #206 on 2026-10-30 (`gh run list --workflow update-openapi.yml`).

A manual `workflow_dispatch` on 2026-10-20 (run 39485625102), while `GIT_TOKEN` still worked, proved the rest of the path: five of eight matrix jobs went through every step, including `Create Pull Request` and `Enable auto-merge`, and opened pull requests for `netlify-api`, `nuki-api-js`, `v0-api`, `keycloak-api` and `vercel-api-js`, which auto-merged into `main`. Two jobs failed in `pnpm generate` because their upstream spec URL is gone (`litellm-api`: `api.litellm.ai` does not resolve; `zoom-api-js`: the old `api-hub` path answers 404); #64 repoints both. `cloudflare-api-js` was still in `pnpm generate` after 27 minutes and was cancelled, so whether it finishes is unknown; each job is now capped at 45 minutes (`timeout-minutes`, which also covers checkout and install), so `cloudflare-api-js` may hit the cap if its generate needs longer. With `fail-fast: false` a failing job does not stop the others, but every hourly run is red while one stays broken.

The slow step was kubb itself. On kubb 5.11.0, a local run on the live Cloudflare spec (7,292 schemas, 3,782 operations, checked 2026-10-26) was still inside the plugin stage after 14 minutes and never wrote a file; sampling showed its main thread in V8's string search. kubb 5.12.5 stopped re-normalizing a `mode: "file"` output on every fragment and merges it once (`@kubb/ast` changelog, kubb-labs/kubb#4396); that this was the whole cause is inferred from the timings below, not profiled. On kubb 5.13.1, the catalog version at the time (#72), the same run takes 28 seconds and peaks at 1.4 GB. The catalog has moved on since (`kubb` in `pnpm-workspace.yaml`, 5.14.2 after #73), and the timing was not measured again. `deduplicateComponents` in `packages/cloudflare-api-js/kubb.config.ts` takes about one second and was not the cause.

The same run then fails in the `biome check --write` post-generate step with `noDuplicateObjectKeys`: `DeleteWebhook` (`/accounts/{account_id}/data-security/posture/webhooks/{webhook_id}`, tag `webhooks`) and `deleteWebhook` (`/accounts/{account_id}/realtime/kit/{app_id}/webhooks/{webhook_id}`, tag `Webhooks`) both become `deleteWebhook` in `cleanOperationIds`, kubb keeps only the first function, and `operationsByTag.webhooks` lists the name twice. `cleanOperationIds` now keeps the first operation in document order on its camel-cased ID and renames each later duplicate after its method and path (`uniqueOperationId` in `packages/openapi-utils/src/kubb/spec-transforms.ts`), with a numeric suffix if that name is taken too, and logs a warning. The data-security operation keeps `deleteWebhook`, which is the one the committed client already exports, and the RealtimeKit one becomes `deleteAccountsAccountIdRealtimeKitAppIdWebhooksWebhookId`. With that, a local `pnpm generate --filter=cloudflare-api-js` on the live spec passes `biome check` in about 15 seconds and the regenerated package typechecks (2026-10-26). None of the other clients' live specs has a colliding ID (checked the same day), so their output does not change.

Upgrading from kubb 5.11.0 to 5.13.1 changed no `types.ts` or `components.ts` for the other seven clients when both versions generated from the same live specs (2026-10-26). Only `schemas.ts` changed: `z.record` keys now follow `propertyNames` (`v0-api`, `litellm-api`), and a `format: hostname` string is no longer validated as a URL (`vercel-api-js`).

A new client must be added to that matrix, to `apps/openapi/src/lib/npm.ts` and `apps/openapi/src/app/page.tsx`, and to `configs/knip.json`.
